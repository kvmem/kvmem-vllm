# DeepSWE：96K/16K、八路与 10M 逻辑历史

本轮按用户要求使用 K=98304、G=16384、最多八路，将客户端、桥接和模型服务的
逻辑上限统一为 10,000,000 tokens（十进制）。该上限不是预留 10M 个 GPU KV
位置，也不意味着模型同时注意到完整 10M 历史。

源实验为 `deepswe-hybrid-lru-300k-20261025-r4`，其 16 个原始结果保留。本轮使用
独立目录，不续写旧答案、不重试低分。当前运行目录是
`deepswe-hybrid-lru-96k-10m-20261025-r2`。

## 固定口径

- NVFP4 权重、FP8 KV、MTP4、block32、sink1312/recent0。
- MeanK/FPS4 各半，FPS4 邻块 ±1 计入预算，关闭图传播与 guided。
- prefill 压力重选继续使用累计 attention；batch16424/chunk2048。
- CPU 历史预算 100,000,000,000 字节、FPS CPU16 workers/cache12GiB，不使用 SSD KV。
- LRU/delete 保持原水位：repository16384、ready_low8192、ready_high9216。
  这些是空闲槽位阈值，约在占用 262144 tokens 时回收到 229376 tokens；
  保护窗口、在途读和共享准入会影响实际释放时刻。
- 原 DeepSWE16、八个独立任务容器、一次尝试、原任务提示与评分器。
  temperature0.6/top_p0.95/top_k20/seed1000/thinking4096 与原循环保护不变。
- 客户端显式预约 16384 输出，匹配已有 native G 上限；关闭客户端自动压缩。

仅在删除式历史 GC、受控 CPU 准入、会话归属及 rolling window 同时开启时，
启动器允许超过原 1M、至多 10M 的逻辑长度。目标模型和 MTP 的实际位置仍沿用
有界窗口坐标，不修改 RoPE 频率。

首个 r1 在模型启动阶段被原生全历史 KV 容量检查拒绝，未执行公开前向或题目。
原始日志和 GPU 组件检查保留并由 r2 的 `startup-recovery-audit.json` 绑定。
修复通过局部配置副本让原生 KV 规划使用 K+G；原生分组、padding、null page、
显存检查和分配仍然执行，并额外要求全部八路的窗口和循环状态同时可容纳。
实际服务、调度、输入身份的逻辑长度仍为 10M，不改安装目录中的 vLLM 源码。

## 执行门槛

有限队列先检查原实验已完成、释放 GPU，并等待 GPU 连续空闲 60 秒。它不会停止
其他 GPU owner，也不创建定时巡检。

1. CUDA 历史索引、FPS4 与 GC 组件测试。
2. 八路原有 Query、尾页、完整 G 生成及恢复预检，验证新增 K 的实际容量。
3. 八路合成会话各自逐段增加至 9,999,968 tokens。每次真实新增最多 32768 输入
   和 64 个固定输出，保留完整 token 身份，不伪造位置或跳过公开输入。每轮强制
   Query 重选，验证回收空洞、续接、边界与预算。
4. 所有长历史会话完成审计和释放后，才开始原 DeepSWE16。

第 3 项累计约 80M 真实输入，需要持续运行；固定输出仅用于控制组件工作负载，
不代表自然 Agent 的生成质量或吞吐。正式 DeepSWE 不使用此输出约束。

长历史预检保存每路 append-only uint32 token journal、请求参数、原响应、输入
哈希、原生计数和资源采样，避免在磁盘重复保存每轮完整长前缀。最终检查：

- 八路实际历史达到目标，终态会话前缀哈希与 journal 对应字节一致。
- 背景退休达到至少每路八个 repository 容量，策略错误和旧代次错误为零。
- 实际公开 prefill 与新增输入数量匹配，无大量历史重算。
- CPU 准入不超额、检查点不降级、主机保留至少 8GiB，不发生 SSD KV I/O。
- 所有历史、检查点和 owned GPU 资源可释放。

页面沿用已有实时界面，单独显示长历史预检进度。若某项失败，保留原尝试与日志，
不绕过门槛进入正式测试。只有执行证据通过后才能称 10M 路径已验证；LRU 永久
删除历史，长期任务质量仍须由正式结果判断。
