# CPU 代表 Key 构建可行性

用户要求先验证：GPU prefill 后把已接受 Key 异步归档到 CPU，由 CPU 挑选每个 32-token block 的 4 个代表 Key，避免构建阶段再次占用 GPU。

## 测量口径

- 本机双路 AMD EPYC 9124：32 个物理核、64 个逻辑 CPU。
- 使用已保存的真实 `niah_multikey_2-0011` Key：261,952 tokens，8,186 个完整 block，16 层 × 4 KV heads × 256 维，原始 FP8 e4m3。
- 固定上一轮已通过验证的 FPS 实现。保留最大范数起点、最远点选择、原始位置打破平局、FP32 距离和原始 Key 值，不引入新的聚类近似。
- 计时包含 Key 复制到独立 CPU slab、CPU FPS、代表值格式转换与缓存发布。每批最多 32 个 block，缓存每次清空。
- 数据读取采用拥有独立目标内存的 mmap 适配器。文件缓存已被输入哈希读取预热；不是冷磁盘读，也不是实际归档接口或模型吞吐测试。
- 没有启动模型，也没有初始化 CUDA。未修改现有实验和服务的线程设置。
- 每轮计时后核验所有代表 token offsets，以及它们对应的原始 Key。完整运行覆盖 2,095,616 个 offsets；全部完全一致。未根据答案或得分重试。

## 结果

先对预定、遍布整个历史的 512 个 block（16,384 tokens）测试线程数：

| CPU 计算线程数 | 构建处理速度，token/s |
|---|---:|
| 1 | 2,427 |
| 2 | 3,844 |
| 4 | 5,807 |
| 8 | 7,800 |
| 16 | 10,040 |
| 32 | 10,523 |

随后做完整历史测试，表中耗时取中位数：

| CPU 线程数 | 完整重复次数 | 261,952 tokens 构建耗时 | 构建处理速度 | 平均占用 CPU 核数，近似 |
|---|---:|---:|---:|---:|
| 8 | 3 | 33.870 s | 7,734 token/s | 7.6 |
| 32 | 2 | 23.157 s | 11,312 token/s | 28.4 |

平均核数是进程 CPU 时间除以墙钟时间，非模型运行时的 CPU 采样。8 → 32 线程处理速度提高约 46.3%，没有随线程数线性增长。尚未做 NUMA 绑定和硬件计数器分析，因此不能把扩展不足完全归因为内存带宽。

## 判断与限制

CPU 计算在数值上可行，而且构建本身可以完全不使用 GPU。这不是免费计算：当前 PyTorch 实现需要相当多的 CPU 资源，且与模型调度、归档、分数维护共享 CPU 和内存带宽。

以历史单请求约 5,875 token/s 的持续 prefill 记录为需求参考，8-thread 组件速度有余量；两者不是同轮并行实测，不能据此宣称等待已隐藏。对八路，11,312 token/s 是整个 CPU 构建任务的总处理能力，不能再乘八。是否跟得上取决于八路同时产生的新 Key 总速率及争用。

另外，vLLM 进程通常限制 Torch CPU 线程；本次 8/32-thread 测试在独立进程内调整，不可直接照搬为服务全局线程设置。服务里的候选 CPU 后台路径不修改全局线程数。要使用多个 CPU 核并控制前台影响，还需要独立、有上限的工作池及模型并发测量。

本轮按用户最新要求止于 CPU 可行性测试。没有启动新的八路模型实验；CPU 后台构建选项保持默认关闭。已经加入的候选后台接入只在接受的完整 block 归档完成后入队，队列有上限、Query 只等本 owner 的在飞工作，失败由原有精确按需 FPS 补建。共享缓存的后续对照配置固定 12 GiB，从总 CPU 历史预算内预留。

候选实现的本轮 CPU 回归共 126 项通过，9 项 GPU 测试跳过。覆盖接受前缀及部分尾块、增量缓存增长、历史空洞、跨 owner 隔离、满队列、读失败补建、Query 等待、回滚、取消、native CPU payload 退休后的读权及资源释放。尚无与模型同时运行的吞吐结论；八路完整诊断还需提高其有界证据日志容量，当前脚本会在准备阶段明确拒绝容量不足。
