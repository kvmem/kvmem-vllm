# FPS4 CPU 构建效率修复与 RULER 重测

## 问题与范围

此前 CPU FPS4 + halo1 的 130 题测试使用模型进程内的单线程 Torch 构建代表 Key。完整历史一次补建约 118 秒，多个 Query 的构建在共享刷新通道排队。此外，缓存把稀疏预构建行排成历史顺序时，可能覆盖尚未移动的有效行，导致已经预构建的 Key 被重新计算。

按用户要求先修复效率，再重新测试。旧实验 `artifacts/ruler-fps-cpu-halo-256k-20261023-r1` 已正常终止并释放自有 GPU 进程；10 题已完成答案与哈希保留在原目录，暂停原因记录于 `user-requested-efficiency-pause.json`。旧冻结代码及结果不变。

## 修改

- 稀疏缓存重排通过交换及位置映射保留已有行；交换前撤销签名，失败时不能读到半发布结果。
- 增加可选原生 CPU FPS 工作池，后台预构建与 Query 缺失补建共用一池。线程数 1–32、同时提交最多 2 个、单次原始 Key 至多 64 MiB，每线程工作区 512 KiB。它不改模型全局 Torch/OpenMP 线程数，不执行 GPU FPS。
- 使用原始 FP8 Key、相同 FPS 规则及最低位置的并列规则；浮点归约近似平分时，对整组原始 Key 调用旧 Torch 实现复核。缓存只保存选出的原始 Key；有限 FP8 到 FP16 的转换精确。
- 原生后台队列容量 1,024 条，只持有元数据和归档读取租约；可容纳两次八路 2K prefill 封存产生的突发。单批仍最多 32 块，归档未完成不能计算，取消及恢复仍按 owner/epoch 隔离。
- 原生 CPU 后端默认关闭，实验显式使用 16 个私有 workers。共享派生缓存仍为 12 GiB，从原有 100 GB CPU 历史总预算中扣除。

Query QK 评分、四个代表 Key 的 max、softmax、预算内 halo1 分组 picker、prefill 累计 attention 均不改。图传播 alpha=0，guided 关闭。共享 Query 刷新通道仍有顺序约束，异步构建不意味着没有 CPU/内存带宽开销。

## 组件验证

真实诊断历史：261,952 tokens，8,186 块，16 层 × 4 KV heads × 256 维原始 FP8 Key。每次派生缓存为空，测量包含读取、FPS、近平分复核、转换及发布；读取原文件的系统文件缓存已预热。核验放在计时区间外。

| 路径 | 次数 | 完整构建耗时 | 相对旧路径 |
|---|---:|---:|---:|
| Torch 单线程 | 3 | 中位 108.210 秒 | 1× |
| 原生 4 workers | 1 | 10.089 秒 | 10.73× |
| 原生 8 workers | 1 | 8.520 秒 | 12.70× |
| 原生 16 workers | 3 | 中位 7.255 秒 | 14.92× |

16 workers 与参考执行两轮交错复测；每次全部 2,095,616 个代表位置及原始 Key/缓存 Key 字节一致。9,648/523,904（1.84%）组触发近平分复核；无工作池容量回退、不支持布局回退或缓存预算泄漏。全程未初始化 CUDA。

结果：`artifacts/query-fps-native-cpu-component-20261023-r1/{summary,full,proof}.json`。该组件提速不能直接作为模型端到端提速。

最终原生 CPU、CPU 集成、异步预构建、增量缓存、GPU FPS 评分/发布、选项与资格回归共 194 项通过（开启 CUDA 测试）。原生并发关闭/异常/容量、稀疏缓存、部分块、原始字节一致性均有覆盖。

## 真实模型重测

先运行固定原始前 8 题的性能资格：`artifacts/query-fps-native-cpu-live-20261023-r1`。完整输入、原始种子和生成上限不缩短；逐题分数仅记录，不按正确率决定重试。需完成实际 CPU 后端、缓存命中、原生 picker、接受统计、预算及 GPU 清理审计。

随后重跑原始每类前 10 题，13 类共 130 题。原始 256K 输入，NVFP4/FP8 KV/MTP4，最多 8 路，K=36,864/G=16,384，sink=1,312/recent=0，batch=16,424/chunk=2,048；生成 8,192、thinking 4,096，与旧测试相同。

固定八题验证已完成，8/8 官方逐题评分为 100；执行审计通过，CPU 后端确认为 native/16 workers，Query 与后台均无 GPU FPS 构建，无工作池容量/不支持布局回退。GPU 清理结果为空。

| 同一原始前八题的指标 | 旧慢测试 | 修复后资格 |
|---|---:|---:|
| Query 复用预构建缓存 | 1,792 / 65,457 块（2.74%） | 65,436 / 65,457 块（99.968%） |
| Query 缓存准备中位数 | 117.67 秒 | 13.56 毫秒 |
| Query 缓存准备合计 | 938.69 秒 | 0.134 秒 |
| 共享组装通道排队中位数 | 408.53 秒 | 5.10 秒 |
| Query 暂缓至恢复中位数 | 511.56 秒 | 7.85 秒 |
| 到首 token 中位数 | 832.41 秒 | 329.85 秒 |

修复后七题无需补建，另一题只补建 21 块。后台预构建合计使用 101.61 秒，分散在八路 prefill 期间；不是消除了计算。新组每题后台等待约 10–70 微秒，零队列溢出延期。Query GPU 评分中位数仍约 0.386 秒，首次评分 1.336 秒，单独计入总阶段成本。

新资格八题请求墙钟约 362.8 秒；旧慢组同八题约 1,320.9 秒。但旧测试是连续 130 题队列，新资格是封闭 8 题波次；新旧输出分别 5,540/6,138 tokens，最终选页集合和生成轨迹也不同。该墙钟变化只能作为观察，不能作为严格同轨迹整轮吞吐加速比。固定 Q/K 的代表位置与字节一致性已由组件测试独立核验；八题同分不等同于完整准确率没有变化。

完整 130 题重测已完成：`artifacts/ruler-fps-native-cpu-halo-256k-20261023-r1`。其 477 个冻结运行文件与通过的八题资格逐一哈希一致；旧组已完成 10 题的 70 份结果/证据文件再次核验未变。
